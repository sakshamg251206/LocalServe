# LocalServe report — MINIMUM scope

All numbers below are generated by `scripts/make_report.py` from `results/minimum/summary.json`
(itself built from the raw per-request JSONL in `results/minimum/raw/`). Prose here does not contain
hand-typed measurements.

## 1. Question

On one 8 GB Apple M2 laptop, serving Qwen3-1.7B with `llama-server`, how much chat traffic
(requests/s) can each quantization × parallel-slot setting take while keeping p95 time-to-first-token
≤ 1.0 s, and what does each quantization cost in fidelity relative to Q8_0?

## 2. Setup

- **Hardware/software:** chip, RAM, macOS, llama.cpp commit, package versions and model sha256s are
  in `results/minimum/manifest.json`.
- **Models:** one F16 source GGUF, quantized locally with `llama-quantize` (no importance matrix), so
  the quant level is the only thing that differs between files.
- **Server:** `llama-server -np {1,4} -c 2048·np -ngl 99` (continuous batching on by default; each slot
  has its own 2048-token KV cache).
- **Gateway:** `max_concurrent = np`, queue of 64, first-token timeout 30 s.
- **Workload:**
  - Open-loop Poisson arrivals.
  - Each request is a unique synthetic 150-word chat prompt (measured prompt tokens: see findings).
  - `max_tokens = 128` with `ignore_eos`, so every config generates the same number of tokens.
  - `temperature = 0`; Qwen3 thinking mode off.
- **Measurement:**
  - TTFT is measured at the client, from send to the first token-bearing SSE event.
  - ITL is the gap between token-bearing events.
  - TPOT = (e2e − TTFT) / (tokens − 1).
  - Output token counts come from the server's `usage`.
- **Repetition and order:**
  - 3 runs × 60 s per point, after 15 s of warm-up.
  - Each repeat visits configs in shuffled order, and rates in shuffled order within a config.
  - 15 s idle between points.
  - Arrival schedules are seeded per (rate, repeat), so every quant sees the *same* arrival times
    (a paired comparison).

### Why open-loop?
A closed-loop benchmark (N clients that each wait for a reply) sends more slowly when the server slows
down, which hides overload ("coordinated omission"). Real users arrive independently, so arrivals are
scheduled in advance from a Poisson process and sent whether or not earlier requests have finished.

### Capacity definition
For each (quant, parallel), all requests from the 3 runs at a rate are pooled, and the nearest-rank p95
TTFT is computed. Rejected, failed and timed-out requests count as infinite TTFT. Capacity is the
highest grid rate where that rate *and every lower rate* meet the SLO. The SLO (1.0 s) was fixed in
`configs/slo.yaml` before measuring.

**Reading KLD.** For each position in the text, the KL divergence compares the full next-token
distribution of the quantized model with Q8_0's. Perplexity only looks at the probability of the true

## 7. Caveats

- **One machine, one run session**, with other apps running. Swapping during measurement is recorded
  per run and counted above.
- **Fanless:** throttling is possible over hours. Interleaving spreads it across configs instead of
  biasing one, and run-to-run spread (Figure 1 bars) shows how much it matters.
- **Grid-limited capacity:** the true capacity lies between the reported rate and the next grid rate.
- **Low-rate points have few requests** (see the data-quality notes), so their p95 is noisy.
- **Quality is measured as KLD on a text subset**, not task accuracy (the STRONG scope adds a
  structured-extraction task check).
- **This is a measurement of one configuration, not a general claim** about Apple Silicon or about
  quantization.
